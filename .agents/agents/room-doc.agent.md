# Room Documentation Agent

## Purpose

Analyze one room from `script_all`. Write a structured markdown document covering:
statistics, memory accesses, objects, enemies, NPCs, external scripts, and oddities.

**No guessing. Only hard facts from the script dump and `in/core.evs`.**

---

## Sources

- **Script dump:** Generated by `list-rooms.cpp` in the SoETilesViewer project. See `copilot-instructions.md` Section 11 for path and ANSI-strip commands.
- **Enum reference:** `in/core.evs` — authoritative source for all named constants. Skip `[CUSTOM]` entries.
- **Existing memory map:** `.github/memory-map.md` — check for existing names before using raw hex.

---

## Input

The orchestrator (or user) provides:
- **Room ID** (hex, e.g. `0x38`)
- **Act classification** (act1 / act2 / act3 / act4 / misc) — always provided, never guessed

---

## Workflow

### Step 1 — Locate room and measure it

Get all room header line numbers in one grep:
`grep -n '^\[0x' <script_all_path> | sed 's/\x1b\[[0-9;]*m//g'`

Find the target room (`N_start`) and the next room (`N_end`). Read only the first 10–15 lines of the room to capture:
- ROM address, data address, enter script address
- Step-on count: from `step-on scripts at ..., (N entries)`
- B-trigger count: from `B trigger scripts at ..., (N entries)`

These counts go directly into the **Statistics** table.

### Step 2 — Read section by section

**If ≤350 lines**: read the whole room in one `sed -n 'N_start,N_end−1p'` call.

**If >350 lines**, read each section separately:

1. **Enter script** — `N_start` to the `step-on scripts at` line.  
   Extract: memory writes/reads, NPC/enemy loads (sprite ID + position), music, camera, external calls, SHOW TEXT opcodes, cutscene content.

2. **Step-on scripts** — `step-on scripts at` to `B trigger scripts at`.  
   Extract: tile coordinate bounds, CHANGE MAP targets, conditional branches.

3. **B-trigger scripts** — `B trigger scripts at` to `N_end−1`, in ≤300-line chunks.  
   Extract: object IDs, persistence flags (address + bit), loot item/type.
   - For **sniff spots**: also capture `$2461` (NEXT_ADD) if written — this is the bonus-loot quantity added on the next sniff visit. Document it in the Objects or B-triggers table.
   - For **enemy drop tables**: document all three prize slots (item ID, rate, quantity). Drop rates and item IDs are interesting for analysis.
   - For **weapon-gated B-triggers**: identify the WEAPON_INDEX or WEAPON_TYPE value and look it up in core.evs (see Step 4).

### Step 3 — Resolve addresses in one pass

Collect all unique addresses from Step 2. Run a single grep:
`grep -n '0xADDR1\|0xADDR2\|...' in/core.evs | grep -v '\[CUSTOM\]'`

Also grep `.github/memory-map.md` for the same addresses. Fill `core.evs Name` from results. Never invent names.

**Music lookup (mandatory):** For every music value found in `PLAY MUSIC` / `CHANGE MUSIC` opcodes, grep for it in the `MUSIC` enum:
`grep -n 'MUSIC\|0xNN' in/core.evs | grep -v '\[CUSTOM\]'`
Always use the enum name (e.g. `CAVES_OF_DANGER`) in the Statistics music field; never write a raw hex value alone.

### Step 4 — Resolve sprite IDs in one pass

Collect every sprite ID from NPC/enemy load opcodes. Run:
`grep -n '0xSPRITE1\|0xSPRITE2\|...' in/core.evs | grep -v '\[CUSTOM\]'`

Cross-reference against the `ENEMY` enum. NPCs are in the same enum, typically under a `// npc` comment group.

**Two calculation methods for ENEMY enum lookup:**
1. **Direct match**: search for the raw hex ID directly in the ENEMY enum.
2. **Shifted value**: some sprite IDs appear as `0xNN>>1` (right-shifted by 1) in ENEMY enum entries — e.g. `NPC 0x8c>>1 = 0x46`. If direct lookup fails, try the shifted form.

**Weapon-gated passages (`$235f` / `$2360`):** Any B-trigger or step-on that reads `CURRENT_WEAPON` (`$235f`) or `CURRENT_WEAPON_TYPE` (`$2360`) is a **metroidvania-style weapon gate**. Always:
- Look up the weapon index in `WEAPON_INDEX` enum (values: SWORD_1=0x02 … SPEAR_4=0x18, BAZOOKA_1=0x1a etc.)
- Look up the weapon type in `WEAPON_TYPE` enum (SWORD=0x00, AXE=0x02, SPEAR=0x04, BAZOOKA=0x06)
- Label the barrier with the weapon name from core.evs, not a raw number
- Do NOT call this an alchemy check; it is a weapon check
- See `docs/patterns.md` — "Weapon-gated passages" section

### Step 5 — Write the file

Output to `docs/rooms/{act}/0xNN-room-name.md`.
Slug: lowercase, spaces → hyphens, `/` stripped.
Example: `[0x38] South Jungle / Start` → `0x38-south-jungle-start.md`
Do not ask for confirmation.

## Output Format

### Mandatory Section Order

Every room document must contain the following sections **in this exact order**. A section may be omitted only under the stated condition; sections may never be reordered.

1. Header block (always)
2. Statistics (always)
3. Overview (always — per `copilot-instructions.md` Rule 15)
4. Connections (omit only if room has zero exits and no transition triggers)
5. Memory Access (always)
6. Objects (omit if no B-triggers / objects found)
7. Enemies (omit if no enemies)
8. Boss (omit if no boss encounter)
9. NPCs (omit if no NPCs)
10. External Scripts (always)
11. Notes (always)

Additional sections (Viewport, Cross-Room Relationships, etc.) may be inserted after Notes.

## Memory Access

| Address | core.evs Name | Size | Op | Section | Notes |
|---------|--------------|------|----|---------|-------|
| 0xXXXX  | NAME or —    | 16b  | W  | enter   | Writes 0x01 on first visit |
| 0xXXXX  | —            | 1b   | R  | obj3    | Bit 0x40; gates NPC unload |

**Size:** `1b` single bit · `8b` byte · `16b` word
**Op:** `R` read · `W` write · `RW` read-modify-write
**Section:** `enter`, `step-on`, `obj N` (B-trigger), or ROM address
**core.evs Name:** exact symbol from `in/core.evs` only; `—` if not found; never invent
**Notes:** include the bit mask for bit-field reads (`Bit 0x40`); mark uncertain inferences `// ?`

Do NOT add emojis or a "Type/Category" column to this table.
Every flag read or written in the room must have its own row — do not group bits.

## Objects

| Obj ID | Group | Persistence Flag | Value Written | Item / Behavior |
|--------|-------|-----------------|---------------|-----------------|
| 0x0000 | 🫙 | `$2268` bit `0x40` | `\|= 0x40` | 🧪 Petal |
| 0x0001 | 👃 | `$228f` bit `0x08` | `\|= 0x08` | 🌿 🍄 Mushroom; NEXT_ADD `0x03` |
| 0x0002 | 🚪 | — | — | Blocks east exit until `$2260&0x40` |

**Group:** category emoji from Section 10 — `🫙` gourd · `👃` sniff spot · `🚪` gate/door · `—` for misc objects with no matching group
**Persistence Flag:** address + bit mask from the flag-check paired with the UNLOAD OBJ opcode; `—` if none
**Value Written:** exact write expression from the script (e.g. `\|= 0x40`, `= 0x01`); `—` if no write found; append `(same as [0xNN])` if this address+value appears in other rooms
**Item / Behavior:** category emoji + optional item-specific emoji + item name; brief description for non-items; `// ?` if unknown
No B-trigger + no persistence flag → write `no persistence` in the Persistence Flag column

## Hard Rules

- **Never invent names, values, or inferences.** Mark uncertain inferences `// ?` and add a `// TODO:` in Notes.
- **Never omit** any object, memory access, external call, enemy, or NPC found in the dump.
- **Never group** multiple objects, enemies, or NPCs into one row. One entity = one row.
- **All table columns required.** Use `—` for unknown; never leave blank.
- **No confidence meta-commentary.** Facts, `// ?`, and `// TODO:` only.
- **Omit entire sections** (Viewport, Objects, Enemies, NPCs, External Scripts) only if nothing is present in the room.
- **NPCs and enemies are always separate sections.** Never write `## NPCs / Enemies`.
- **Statistics table is mandatory.** Fill counts from the section header lines in the dump.
- **Never claim the file is complete** if context ran out — end Notes with `// INCOMPLETE: stopped at line N`.
- **Never identify an enemy or NPC as "NPC 0xNN"** — look up the ENEMY enum. If not found, write `?` and add a `// TODO: look up ENEMY 0xNN` in Notes.
- **Never guess real-world names** for NPCs from dialog or context (e.g. "Alma", "the prophet"). Quote dialog verbatim or use the ENEMY enum name.
- **Memory table: no emojis, no Category column.** Use the 6-column spec format exactly.
- **Drop table belongs in Statistics**, not a separate section.
- **Every `?` value generates a `// TODO:` in Notes** naming the specific unknown.
- **Check `docs/patterns.md`** before documenting a flag or script — if it's a known shared pattern, reference it rather than re-explaining it.
- **Category emojis (Section 10 legend) are mandatory** in the Objects Group column and when prefixing item references outside the Memory Access table. Item-specific emojis (e.g. 🍄 for mushroom ingredients, 🍯 for honey) may accompany the category emoji **only if used consistently throughout the entire document**. Never use an item-specific emoji that visually duplicates a category emoji from the legend. Never use any emoji inside the Memory Access table.
- **Never write an “Enter Logic” or “Enter Script” pseudo-code section.** Behavioral reconstruction of enter scripts belongs in Notes bullets, Memory Access rows, and External Scripts rows — not as pseudo-code.
- **Sections must follow the mandatory order** defined in the Output Format section. Do not add top-level sections that duplicate the mandatory ones, and do not reorder them.
- **WindWalker is a flying machine, not alchemy.** `$22dc&0x08` = WindWalker unlocked (machine obtained). Do not call it a spell or alchemy. Similarly, Levitate is alchemy and is separate from the WindWalker.
- **Music must use names from core.evs MUSIC enum.** Never write a bare hex value for music.
- **`$235f`/`$2360` checks are weapon gates, not alchemy checks.** Identify the weapon tier and type from core.evs enums; note whether the condition is an exact match or a range (the dump uses decimal values — translate to WEAPON_INDEX / WEAPON_TYPE hex).
